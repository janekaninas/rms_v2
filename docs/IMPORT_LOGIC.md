Covers every ingestion path listed on the Daily Upload page. All imports must use bulk insert/upsert (no per-row database round trips — see `PRODUCT_SPEC.md` performance requirements) and must support a **parse → validate → preview → commit** flow so a bad file can be caught before it touches the ledger.

General shape for every import type:

1. Parse the uploaded file into rows (CSV or XLSX; VHP exports observed as XLSX-style tabular data, Guesty as CSV-style).
2. Validate: required columns present, types parseable (VHP number fields arrive as locale-formatted strings, e.g. `'1,363,541.00'`, and must be parsed accordingly — legacy sheets do this with `NUMBERVALUE(x,".",",")`), dates parseable.
3. Resolve lookups: channel (via `channels`/mapping), villa (via `room_villa_mapping`). Unresolved lookups do not fail the import — they commit with a null reference and immediately raise a `reconciliation_exceptions` row (`UNKNOWN_CHANNEL` / `UNKNOWN_VILLA`), matching the brief's instruction to make problems visible rather than hide them (and matching the legacy sheet's own `#N/A` cells, which is exactly this failure mode surfacing today, just invisibly).
4. Preview: show counts (new / would-update / unchanged / unmatched / errors) before committing, using the match keys defined per import type below.
5. Commit: bulk upsert in a single transaction; write one `imports` row summarizing the result (filename, upload time, rows processed, new, updated, ignored, unmatched, errors) per the required post-upload summary.

## 1. New Bookings (Aasha / VHP)

Legacy source: `Bookings` sheet. Columns of interest: `Reservation Number`, `Created Date`, `Arrival`, `Departure`, `Room Number`, `Room Type`, `Room Rate`, `Total Revenue`, `Guest Name`, `Reservation Name` (channel/agent), `Status`.

- **Match key**: `reservation_number` (scoped to portfolio=AASHA).
- **Upsert rule**: if the reservation number already exists, update its mutable fields (arrival/departure/room/rate/guest/channel/status) rather than inserting a duplicate — "new data should update existing reservations where appropriate rather than creating duplicates." If any of arrival, departure, room, or rate differ from the stored value on an update, this is itself a signal worth surfacing (see `ROOM_CHANGE_DETECTED` / `ARRIVAL_DEPARTURE_MISMATCH` in `DATA_MODEL.md` §6) rather than silently overwriting — this generalizes the intent of the dedicated Room Change Log (§4) to ordinary re-uploads of the Bookings file, since in practice a changed reservation can show up either way.
- **Status handling**: the raw `Status` field can itself say `Cancelled` (observed in sample data) even inside the "New Bookings" export — do not assume this file only contains active reservations. Map `Status = "Cancelled"` → `reservations.status = CANCELLED` and write a `reservation_status_history` row, exactly as the dedicated Cancellation import would (§2). This mirrors the legacy `Bookings!AE` (`STATUS = IF(Status="Cancelled","NOK","OK")`) logic.
- **Channel/villa resolution**: channel from `Reservation Name` (trimmed) via `channels` mapping (fallback: blank → `Direct`); villa from `Room Number` via `room_villa_mapping` (fallback: `Room Type` when room number is unavailable/status not OK), replicating `Bookings!AI` (`IF(status OK, lookup by room, else lookup by room type)`).
- **Derived fields computed at import time, not stored as raw**: `nights = departure − arrival`; `system_gross_revenue`: prefer the raw `Total Revenue` figure when present and parseable, else fall back to `Room Rate × nights` (legacy `Bookings!AR`: `IF(Total_rev_booking<>"", that, Room_Rate)`, then `×nights`). A mismatch between the two (legacy `Check price`) is recorded informationally, not blocking (see `FINANCIAL_LOGIC.md` §10 item 8).

## 2. Cancelled Reservations (Aasha / VHP)

Legacy source: `CANCEL` sheet. Columns: `Reservation Number`, `Cancel Date`, `Cancel Time`, `Cancel Reason`, plus the reservation's own descriptive fields (largely redundant with `Bookings`).

- **Match key**: `reservation_number`.
- **Rule**: **never delete.** If the reservation exists, set `status = CANCELLED`, insert a `reservation_status_history` row with `effective_at` = Cancel Date/Time and `reason` = Cancel Reason. If the reservation does *not* yet exist (a cancellation arriving before/without ever seeing the original booking — plausible if the export windows don't perfectly overlap), still create a minimal reservation record marked cancelled from the available fields, and raise an informational reconciliation note rather than silently dropping the row.
- Note the redundancy with the `Status` field inside the Bookings export itself (§1) — both paths must converge on the same `reservation_status_history` mechanism so a reservation cancelled via either route ends up in the same state, and re-processing the same cancellation twice (idempotency) must not create duplicate history rows for the same `(reservation_id, effective_at)`.

## 3. Room Revenue Breakdown (Aasha / VHP) — the authoritative daily grain

Legacy source: `ROOM REV` sheet. Grain: one row per reservation per stay-date. **`[v0.6 — confirmed]`** Jane confirmed one export file always covers a single stay date — the stay date is **entered manually at upload time**, not read from a per-row date column in the file (a "CURRENT DATE" column, if present, is not trusted). The match key is therefore (`Reservation Number`, the manually-entered stay date), applied uniformly to every row in the file.

- **Match key**: (`reservation_id`, `stay_date`) — composite unique key on `daily_revenue`.
- **Upsert rule**: "Re-uploading the file should update existing daily revenue rows, not duplicate them" — explicit requirement, enforced by the composite unique constraint plus an `ON CONFLICT DO UPDATE` (or equivalent) bulk upsert.
- **Unmatched rows**: a Room Revenue row whose `Reservation Number` doesn't exist in `reservations` yet → raise `DAILY_REVENUE_WITHOUT_BOOKING`, still store the row (`reservation_id` null, `DATA_MODEL.md` §2) so it can be reconciled once the booking arrives, rather than being dropped.
- **`[v0.6 — corrected]` This import only ever supplies *actual* per-night figures — it never establishes a reservation's authoritative total, and it never determines whether financial figures can be computed at all.** That role belongs to the Booking/Arrival Report total (`reservations.system_gross_revenue`/`final_gross_revenue`) from the moment a reservation exists — see `FINANCIAL_LOGIC.md` §7a for the full confirmed model. Concretely:
  - **OTA channels**: committing an actual Room Revenue row for a stay-date recomputes that reservation's *entire* nightly allocation — the newly-actual night uses its real figure, and every remaining not-yet-actual night is re-estimated as `(Authoritative Reservation Total − SUM(actual nights so far)) / (nights still unresolved)`. The authoritative total itself is never changed by this import. Once every night is actual, compare the sum to the authoritative total and raise `ROOM_REVENUE_TOTAL_MISMATCH` (`DATA_MODEL.md` §8) if they don't reconcile — never silently adopt the actual sum as the new total.
  - **Direct/Individual/Travel-Agent channels, no approved override**: same progressive-estimate mechanics as OTA, but the reservation also carries an open `MANUAL_REVENUE_OVERRIDE_PENDING` exception the whole time, since the underlying system total isn't trusted for these channels.
  - **Direct/Individual/Travel-Agent channels, approved override (confirmed)**: this import's per-night figures for that reservation are **not** used at all — `daily_revenue` rows are instead generated as an even split, `approved_manual_revenue / stay_nights`, one `STAY`-type row per night (`FINANCIAL_LOGIC.md` §7/§7a-B). The file is still accepted and counted in the import summary for audit purposes; it simply has no effect on that reservation's allocation. Implement the override-driven allocation as one clearly named, testable rule — not inline conditional logic scattered across the financial engine.
- **Financial computation happens at import/recompute time** using the configurable commission/PB1/tax-profile rules (`FINANCIAL_LOGIC.md`), not by trusting any pre-computed revenue figure in the source file — the source file only supplies `commercial_revenue_basis_amount` (nightly rate, `[RENAMED]` from `gross_revenue` — see `DATA_MODEL.md` §2); commission/VAT/PB1/net are always derived server-side so that a later change to commission rules can be recalculated without re-uploading. **`[CORRECTED — no silent fallback]`** If no `channel_payment_rules` row resolves for this reservation's channel+villa+date, do not compute commission/VAT/PB1/net using an assumed default — raise `MISSING_PAYMENT_RULE` and leave this reservation's figures incomplete/not final (`FINANCIAL_LOGIC.md` §5, `DATA_MODEL.md` §4/§8).

## 4. Reservation Change Log `[Day-7 scope note]`

If reliable automated detection (the auto-apply/always-flag classification below) cannot be completed with confidence by Day 7, it is acceptable to ship Day 7 with change-log rows landing in Reconciliation as manual-review items across the board (i.e., "always-flag" for everything, no auto-apply yet) rather than delay the production launch — refining the auto-apply boundary is an acceptable Days 8–14 follow-up. Do not silently apply an unconfirmed auto-apply rule just to appear more automated by Day 7; a manual-review-everything fallback is the safe default.


Legacy source: `Room change` sheet — paired before/after columns (Arrival, Departure, Quantity, Adult, Child, Compliment, Room Type, Room Number, Arrangement Code, Rate, Guest Name) plus a single computed flag, `ROOM CHANGE = IF(before_room = after_room, "NO", "YES")`. **No other field currently gets an automatic before/after comparison** — rate, date, and occupancy changes pass through unflagged today.

For the new system, generalize this: for every tracked field (room number, room type, arrival, departure, rate), compare before/after on each change-log event and classify:
- **Auto-apply candidates** — changes that don't affect revenue or reported nights and have no ambiguity (e.g., a room-number change within the same villa/room-type, guest name correction). These may update the reservation directly, logging the change for traceability.
- **Always-flag candidates** — any rate change, any arrival/departure change (these affect nights, occupancy, and revenue), and any room change that also changes the mapped villa. These must create a `reconciliation_exceptions` row (`ROOM_CHANGE_DETECTED` / `ARRIVAL_DEPARTURE_MISMATCH` / `AMBIGUOUS_CHANGE_LOG_EVENT`) rather than silently updating the ledger.

**NEEDS CONFIRMATION**: the exact auto-apply vs. always-flag split above is a reasonable starting point inferred from the brief's instruction ("apply reliable changes automatically, or flag ambiguous cases... do not silently overwrite questionable information"), but the specific boundary was not specified and must be confirmed with Jane before Milestone 8 — do not treat the split above as settled.

## 5. Balinest / Guesty — snapshot replacement, not incremental

Guesty exports do not reliably carry a booking-creation date, and per the brief, "do not automatically assume that a missing reservation is a cancellation unless the business rule can establish that."

- **Model**: each Balinest upload is a full snapshot of Balinest's current reservation position (all confirmed/relevant reservations as of that moment), recorded via `balinest_snapshots` (see `DATA_MODEL.md` §3).
- **Processing**: within one snapshot, reservations are matched by whatever stable identifier Guesty provides (needs confirmation of the actual unique key available in a real Guesty export — the sample data has no obvious reservation-number-equivalent column visible in the header row; `LISTING ID` + `GUEST'S NAME` + `CHECK-IN` is a plausible composite fallback but should not be assumed without checking a live export).
- **Do not diff-and-cancel**: a reservation present in snapshot N and absent from snapshot N+1 must **not** automatically become `CANCELLED`. Until a specific, confirmed rule exists (e.g., "if a reservation's arrival date has passed, its disappearance is just normal lifecycle, not a cancellation signal"), such disappearances should surface as informational only, if at all — flagged `NEEDS CONFIRMATION`, no default behavior should be implemented here without sign-off.
- **History**: retain every snapshot's raw data (via `imports.raw_file_ref` and `balinest_snapshots`) so that a later audit or a future confirmed diffing rule can be applied retroactively without having lost the source data.
- **Source tagging**: every resulting reservation/revenue row must carry `portfolio = BALINEST` so it never gets aggregated into Aasha-only views by accident, per the requirement to be able to "distinguish AASHA / BALINEST."

## 6. Villa & channel mapping (configuration, not import-time guessing)

Both the Aasha and Balinest import paths depend on `room_villa_mapping` and `channels` (`DATA_MODEL.md` §1) being maintained as configuration (the "Villa Mapping" and "OTA / Channel Rules" pages), not inferred fuzzy-matched at import time. An import should only ever *use* these tables, and raise a reconciliation exception when a lookup fails — it should never silently create a new villa or channel on the fly. This directly replaces the legacy `Mapping` sheet, which today is the single point of failure behind every `#N/A` villa observed in the sample data (9 of 4,395 rows).

## 7. Performance constraints on all of the above

- Parse the whole file into memory/a staging structure first; resolve all lookups with batched queries (e.g., one query to fetch all relevant `channels`/`room_villa_mapping` rows, not one query per source row).
- Perform the actual write as one bulk upsert statement (or a small constant number of them) per import, not one statement per row.
- The preview step should be computable without writing anything (a dry-run diff against current state), so a rejected/cancelled preview leaves no trace.

These constraints apply equally to the new import types below (§8–§10).

## 8. `[NEW — Day-7 critical]` OTA Settlement import

Build **one generic settlement-import framework with per-channel column mapping and format adapters**, not a bespoke parser per OTA. The channel-agnostic schema (`DATA_MODEL.md` §7, and the `channel_payment_rules` model in §4) means additional OTA parsers are additive later, not a redesign.

**Confirmed Day-7 priority order (Jane, this revision): Airbnb first, then Booking.com, then Expedia.** This reverses the earlier assumption that Booking.com should come first. The reasoning: Airbnb's `payment_model = NET_REMITTANCE` with `source_amount_basis = NET_AFTER_OTA_DEDUCTIONS` means the PMS/VHP figure is already Airbnb's net payout — there is no deduction math to validate, so Airbnb is the fastest channel to get end-to-end working and provides an early, low-risk proof of the whole settlement pipeline (parse → batch/lines → match → allocate). Booking.com (non-Bracha) is the first channel that actually exercises the commission/payment-service-fee/VAT deduction formula against a real worked example (`FINANCIAL_LOGIC.md` §6/§11). Expedia, being `GROSS_REMITTANCE_INVOICE_LATER`, is last because its settlement file behavior (an invoice showing "Amount to be paid = IDR 0" until a separate collections/invoice cycle) is the least like an ordinary payout and benefits from the other two adapters existing first as a reference. Build the generic engine and mapping config so that adding the second and third channels on Day 5 is a matter of adding a mapping + adapter, not new reconciliation logic.

1. **Parse**: read the uploaded file (CSV/XLSX) into rows using a configurable column mapping (per channel, since every OTA's settlement report has a different layout) — the mapping itself (which source column is "amount," "reservation reference," "line type," etc.) is configuration, stored alongside `channels`/`channel_payment_rules`, not hardcoded per file format in application code. The real Airbnb/Booking.com/Expedia file formats have not yet been supplied — request a real sample export of each before finalizing its mapping (`FINANCIAL_LOGIC.md` §10 item 19); do not guess a layout from memory of "typical" OTA reports.
2. **Validate**: required columns present per that channel's mapping; amounts parseable (locale-formatted numbers, same caution as VHP exports); dates parseable.
3. **Batch and lines, with mandatory idempotency**: create one `ota_settlement_batches` row per payout (or per file, if the file is naturally one payout), matched against existing batches by natural key `(channel_id, batch_reference)` when the export provides a stable batch/payout reference, else by a deterministic `dedupe_hash` computed from the batch's channel, period, and total (`DATA_MODEL.md` §7). Re-uploading the same settlement file must never create a duplicate batch — a matching batch is treated as already-imported and skipped (or, if `allow_reprocess` is explicitly requested, superseded rather than duplicated). Within a batch, create one `ota_settlement_lines` row per detail line, tagged with `line_type` (`BOOKING_PAYOUT`/`ADJUSTMENT`/`REFUND`/`CORRECTION`/`FEE`/`OTHER`), each matched against existing lines by `external_line_reference` when present, else by a per-line `dedupe_hash` — so a partially-re-uploaded or overlapping file updates/skips at the line level, not just the batch level.
4. **Reservation matching/allocation**: attempt to match each `BOOKING_PAYOUT` line's `raw_reservation_reference` against `reservations.reservation_number` (allowing for the OTA's reference format differing slightly from VHP's — e.g. a prefix or suffix — per a channel-specific normalization rule, itself configuration rather than inline string-fiddling code). An exact, unambiguous match creates a `settlement_reservation_allocations` row automatically. A line that matches multiple candidate reservations, or none, is left `UNMATCHED`/`PARTIALLY_MATCHED` and surfaces in Reconciliation — **never discarded, never force-matched**. A line whose reservation resolves to a villa/channel combination with no matching `channel_payment_rules` row raises `MISSING_PAYMENT_RULE` (`DATA_MODEL.md` §8) rather than silently falling back to a default rate.
5. **Preview**: show batch totals, line counts by type, and match/unmatched counts before committing.
6. **Commit**: bulk insert the batch/lines/allocations; write the standard `imports` summary row (`import_type = OTA_SETTLEMENT`).
7. **Manual entry fallback**: for an exceptional settlement that doesn't come as a file (a one-off correction, a channel with no bulk export), support direct manual entry of a batch + lines through the same underlying tables — the UI path differs, the data model and reconciliation behavior do not.
8. **`[cross-reference]`** API integration with any OTA extranet is explicitly out of scope for Day 7 and for the whole two-week build — this import framework is designed so a future API feed can populate the same `ota_settlement_batches`/`ota_settlement_lines` tables without changing the reconciliation/allocation model downstream.

## 9. `[NEW — Day-7 critical]` Bank Mutation import

**Confirmed Day-7 source (Jane, this revision): BCA** is the first (and for Day 7, only required) bank account/source. A real BCA export sample is still needed to finalize the exact column layout and dedup fields (`FINANCIAL_LOGIC.md` §10 item 19-adjacent — request this on Day 1) — the steps below describe the shape of the import regardless of the exact confirmed layout.

**Format preference, strongest to weakest**: (1) a structured, machine-readable export — CSV or XLSX, whatever BCA's internet/mobile banking or corporate portal offers as a downloadable statement — is strongly preferred and should be the only path built for Day 7; (2) failing that, a machine-readable PDF/text statement that a deterministic parser (not OCR) can extract fixed-position or delimited fields from; (3) manual entry of individual transactions as a last-resort fallback for a period with no usable export, through the same underlying `bank_transactions` table. **OCR-based statement parsing is explicitly out of scope for Day 7 and should not be built as the primary path** — it introduces exactly the kind of non-deterministic, hard-to-idempotency-key data entry this import is designed to avoid; if BCA genuinely offers no structured export, escalate that as a blocker rather than building an OCR pipeline under deadline pressure.

1. **Parse**: read the bank statement export in whichever structured format BCA actually provides (confirm on Day 1 — see above).
2. **Validate**: transaction date, amount (or debit/credit pair), description parseable.
3. **Idempotency (mandatory — re-uploading the same statement period must never create duplicate transactions)**: match incoming rows against existing `bank_transactions` by `external_line_ref` when the export provides one, else by the `dedupe_hash` composite (`DATA_MODEL.md` §6/§8). A row matching an existing key is counted as `ignored`/`unchanged`, never re-inserted. Once a real BCA export is in hand, confirm which fields (reference number, running balance, description, amount, date/time) are stable enough to anchor `external_line_ref`/the hash — do not assume a bank always provides a usable unique reference.
4. **Preview**: new vs. already-seen (idempotent-skip) vs. error counts before committing.
5. **Commit**: bulk insert new `bank_transactions`; write the standard `imports` summary row (`import_type = BANK_MUTATION`), plus a `bank_imports` row recording the statement period covered and `bank_account_id` (BCA for Day 7).
6. **Matching to settlements** happens as a separate step/page (Bank Reconciliation, `REPORTING_LOGIC.md`), not as part of the import itself — importing a statement should never silently auto-allocate ambiguous matches; see §"Bank matching" logic there for the deterministic-vs-manual-confirmation rule.

## 11. `[NEW — permanent import type]` Baseline / Arrival Report Snapshot import

Legacy source: `Arrival Report` sheet. Confirmed by Jane (this revision) as a **permanent, reusable import type** — not a one-time Day-2 migration script. It serves two purposes with the same mechanism: (a) the initial data migration, seeding the platform with every currently-in-house reservation at go-live, and (b) **new-villa onboarding**, step 7 of the villa onboarding workflow (`DATA_MODEL.md` §1) — whenever a new villa joins Aasha's management with existing forward bookings already on the books (made before the villa was configured in the platform), its current reservation position is seeded the same way, rather than needing a bespoke one-off script per villa.

- **Import type**: `BASELINE_RESERVATION_SNAPSHOT`, alongside `NEW_BOOKINGS`/`CANCELLATIONS`/`ROOM_REVENUE`/`OTA_SETTLEMENT`/`BANK_MUTATION` etc. in the `imports.import_type` enum (`DATA_MODEL.md` §5).
- **No new table required**: this import reuses the existing `reservations` / `reservation_status_history` upsert mechanism (§1–§2 above), not a separate staging model — a baseline row for a reservation not yet in the system is a plain insert; a baseline row for a reservation already present (e.g., re-running the import, or a new villa whose bookings partially overlap an already-imported period) is a plain update via the same `reservation_number` match key.
- **Scope, per run**: a baseline import is scoped to a specific villa (or, for the initial migration, the whole portfolio) and an as-of date. It is a snapshot of "everything currently on the books for this villa as of this moment," not a delta.
- **No auto-cancel-by-omission**: exactly as with Balinest snapshots (§5), a reservation that existed in a prior baseline/import but is absent from a new baseline run must **not** be automatically marked cancelled. Absence is not a signal on its own — surface it informationally if at all, never as an automatic status change.
- **Same parse → validate → preview → commit flow** as every other import type: parse the Arrival-Report-style export, resolve villa/channel/room lookups (raising `UNKNOWN_CHANNEL`/`UNKNOWN_VILLA` exactly as in §1, never silently creating a new villa/channel), preview new/update/unchanged/error counts, then bulk commit with a single `imports` summary row.
- **Interaction with the financial engine**: baseline-imported reservations flow through the same commission/VAT/PB1/Expected-Settlement calculation as any other reservation (`FINANCIAL_LOGIC.md`) — a baseline import is a data-entry-path distinction only, never a financial-treatment distinction. A baseline-imported reservation for a villa with no `channel_payment_rules`/`villa_tax_profile_assignments` configured yet is exactly the scenario the villa onboarding workflow's ordering (configure the villa and its rules *before* importing its baseline) is meant to prevent — but if it happens anyway, it must raise `MISSING_PAYMENT_RULE`/an equivalent exception, not default silently.
