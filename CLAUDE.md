# AASHA Villa Management Platform — Instructions for Claude Code

> **Revision note:** This project started as "AASHA Revenue Portal" (commercial revenue reporting only) and has been expanded three times: first into a four-domain platform (Commercial, Revenue Reconciliation & Settlement, Operations & Expenses, Finance & Owner Reporting); then re-sequenced around a **7-day live production launch** (Booking → Revenue → Expected Settlement → OTA Settlement → Bank Reconciliation) followed by a **Days 8–14 Phase 2** (Expenses, Management Fee, Owner Statements/Payout, P&L); then updated with **Jane's confirmed business rules** resolving several prior `NEEDS CONFIRMATION` items (portfolio target, Bracha treatment and cutover date, PB1 withholding, OTA payment models, cancellation revenue, villa-visibility rules, settlement priority order, no-silent-fallback for an unresolved payment rule — see rules 17–20 below). All of the rules below apply to the whole platform, at every phase — the phasing changes *when* something gets built, never *how carefully*.

## Authoritative documents

- `docs/PRODUCT_SPEC.md` — what this system is, the four domains, navigation, and the Day-7-vs-Phase-2 scope split.
- `docs/DATA_MODEL.md` — the full schema: reservation/revenue core, settlement/bank reconciliation, expenses, and owner-finance tables, keyed to specific legacy worksheet columns/formulas where they originate there, and to the platform-expansion brief where they're new.
- `docs/FINANCIAL_LOGIC.md` — commission, VAT, PB1, net revenue formulas, the confirmed `channel_payment_rules` model (`source_amount_basis`/`payment_model`), Expected Settlement/OTA Settlement/Bank Receipt as distinct concepts, expense economics (`paid_by`/`borne_by`), management fee, and the owner payout waterfall — and a **Conflicts & NEEDS CONFIRMATION register (§10)**, now split into resolved-by-Jane's-confirmation and still-open, that has only grown and been explicitly resolved item-by-item, never silently resolved, across every revision.
- `docs/IMPORT_LOGIC.md` — parse→validate→preview→commit for every import type: the permanent Baseline/Arrival Report Snapshot import, VHP bookings/cancellations/room-revenue/change-log, Balinest/Guesty snapshots, OTA settlement files (Airbnb → Booking.com → Expedia priority), BCA bank mutation files, and (Phase 2) expense imports.
- `docs/REPORTING_LOGIC.md` — how every report is calculated, including Road to Target, Channel Performance, Settlement Reconciliation, Bank Reconciliation, the Reconciliation Dashboard, the Accounting Handoff view, and the Phase 2 Expense/P&L/Owner reports.
- `docs/DESIGN_SYSTEM.md` — visual language, tokens, component mapping, including the reconciliation/settlement status badge system.
- `docs/IMPLEMENTATION_PLAN.md` — the Day 1–7 production launch critical path and the Days 8–14 Phase 2 plan.

## Rules for any future session working on this codebase

1. **These documentation files are authoritative.** If code and docs disagree, the docs win unless Jane explicitly changes the docs first.
2. **Do not invent business rules.** Every `NEEDS CONFIRMATION` item (`FINANCIAL_LOGIC.md` §10 is the master register) is a stop sign, not a placeholder — surface it and wait, don't guess. This applies with particular force to anything feeding **Expected Settlement**, since a wrong assumption there silently distorts every settlement/bank variance the Day-7 launch is built around. Several items are now resolved by Jane's confirmation (§10's "Resolved by Jane's confirmation" list) — treat those as settled, but the items still marked "still open" or newly opened by that revision are exactly as much a stop sign as ever.
3. **Financial-logic blockers get raised on Day 1, not discovered mid-build.** Most of the highest-risk items (the Bracha PB1/service-charge conflict and its cutover date, the near-zero-commission-for-most-OTAs question, whether PB1 is withheld by any OTA, and Bracha's Booking.com rate) are now **resolved** by Jane's confirmed rules — but the remaining open items in `FINANCIAL_LOGIC.md` §10 (the full villa×channel `channel_payment_rules` matrix beyond the four confirmed combinations; real OTA/BCA file formats) must have an answer — even a provisional, clearly-flagged one — before Day 3's financial engine and Day 5's settlement work are built. An unresolved combination is never guessed at in the meantime — see rule 20.
4. **Do not change financial logic without explicit approval** — commission rates, VAT treatment, PB1 calculation, villa tax profiles, manual-override precedence, settlement-basis rules, management fee structures, and the owner payout waterfall are all sensitive. "Fixing" something that looks like a bug still requires sign-off, referenced back to the specific `FINANCIAL_LOGIC.md` §10 item.
5. **Revenue, Expected Receivable, OTA Settlement, and Cash Received are four distinct concepts** (`FINANCIAL_LOGIC.md` §8) — never merge them into one number just because they usually coincide. Track and display all four, with their variances, even when a variance is zero.
6. **`paid_by` and `borne_by` are distinct fields on every expense** (`DATA_MODEL.md` §9) — never collapsed into one. An expense Aasha pays for but the owner economically bears must flow to that owner's statement, not into Aasha's P&L.
7. **Approved or paid owner statements/payouts are never silently rewritten.** A correction after approval/payment (or after its `accounting_periods` row is closed) goes through a `statement_adjustments` record posted into a later open period.
8. **Villas — and channels, owners, bank accounts, and commission/tax/payment rules — are configuration, never hardcoded.** No page, report column, calculation, or import may assume a fixed villa list. A villa created through the Configuration UI (with its immutable `villa_code` and `management_start_date`/`management_end_date`) must be immediately usable everywhere without a code change or deployment. Occupancy and reporting denominators respect `management_start_date`/`management_end_date` — a villa never reads as "0% occupied" for a period before Aasha managed it (or after management ended). **`[Confirmed rule]`** A villa's `active` flag is a *current-config* filter only (dropdowns, the Configuration page's default list) — it must **never** be used to filter a *historical* report. Historical reporting (Monthly Performance, Summary, any past-period view) includes a villa whenever the reported period overlaps that villa's `management_start_date`/`management_end_date` window, regardless of its current `active` value.
9. **Do not redesign the information architecture without explicit approval.** The four-domain structure and the navigation map in `PRODUCT_SPEC.md` §5 are intentional; simplify by merging conceptually-adjacent pages during implementation if that's genuinely cleaner, but don't add modules beyond what's documented, and don't build a page just because a menu item exists in the conceptual map before its underlying data/workflow is ready.
10. **Keep database/reporting logic separate from presentation**, and keep each domain's frontend state narrow — adding settlement, bank, and expense modules must not produce one monolithic frontend state holding reservations, revenue, settlement, bank transactions, and expenses all at once. Each page fetches only the aggregated slice it needs.
11. **Optimize for correctness, traceability, and performance, in that order**, every revenue and settlement/bank/expense figure must be drillable to its underlying source rows (`REPORTING_LOGIC.md`'s drill-down sections) — no black-box totals anywhere in any domain. Performance means indexed server-side aggregation, bulk upserts (never one DB call per row), idempotent imports (re-uploading a file never duplicates data — this is explicitly mandatory for bank mutation imports), and pagination/virtualization on large tables.
12. **Two-week/Day-7 prioritization applies — follow `IMPLEMENTATION_PLAN.md`'s day sequence.** Do not defer anything on its do-not-defer list (correct financial calculations, idempotent imports, auditability, villa configurability, effective management dates, the settlement allocation model, bank reconciliation, production deployment) to protect a deferrable item (forecasting polish, advanced charts, mobile, API integrations, fuzzy/ML matching, multi-level approvals, pixel-perfect exports, animation). If a day's scope is genuinely at risk, cut from the deferrable list first and say so — don't quietly ship a shortcut on something load-bearing to stay on schedule.
13. **Do not overengineer post-MVP features before the core workflow works.** Expenses, management fee, owner statements/payout, and P&L (Phase 2, Days 8–14) should not be started, even partially, before the Day-7 Booking→Bank chain is live and verified in production — and even then, build only what `PRODUCT_SPEC.md` §8's Phase 2 list actually asks for, not a more general framework than the documented need.
14. **Deployment is continuous from Day 1**, not a Day-7 task. Every day's completed feature is verified in the hosted production environment, not only locally.
15. **Never delete reservation or cancellation history.** Cancelled reservations stay in the ledger with full status history; Balinest snapshots are retained for audit even though they use a replace-not-diff model. The same spirit applies to the new modules: settlement/bank allocations and owner-statement corrections are additive/adjusting records, not overwrites.
16. **Do not install unnecessary dependencies**, and do not choose an architecture that requires the browser to reproduce server-side calculation or reconciliation logic — commission/VAT/PB1, settlement/bank matching, and the owner payout waterfall are all computed server/database-side, once, correctly.
17. **The portfolio revenue target is explicit configuration, never derived.** The current confirmed figure is IDR 1,500,000,000/month for the 33-villa portfolio (26 Aasha + 7 Balinest), stored as its own `revenue_targets` row (`villa_id IS NULL`). Do not compute a portfolio target by summing villa-level targets, and do not let the two figures be forced to reconcile — villa-level targets remain independently configurable and may not sum to the portfolio figure.
18. **PB1 is never withheld or remitted by any OTA, for any channel — confirmed.** It is Aasha's own separate remittance to local government. No calculation may treat PB1 as reducing Expected Settlement; `channel_payment_rules.pb1_withheld_by_ota` defaults to `false` and changing that default for any channel requires the same sign-off as any other financial-logic change (rule 4).
19. **Settlement/commission behavior is resolved by channel and, where configured, villa or villa-group — never by channel name alone, and never hardcoded in a component.** Use `channel_payment_rules` (specificity order: villa > villa-group > channel-default, effective-dated) as the single source of this logic. Bracha's legacy 21%-service-charge/PB1-exemption treatment is **retired** as the default — it survives only as an effective-dated historical `villa_tax_profile_assignments` row for stay dates before **2026-08-01** (the confirmed cutover date), and must never be the fallback behavior for a new or unconfigured villa/period; Bracha's Booking.com commission is confirmed at **18%**, effective from that same date. The confirmed Day-7 OTA settlement build-and-test priority order is **Airbnb → Booking.com → Expedia** (not Booking.com-first, an earlier assumption this revision corrects).
20. **`[Confirmed rule]` An unresolved `channel_payment_rules` lookup has no silent fallback.** If no rule matches a reservation's channel + villa + date, do not assume `NET_REMITTANCE`, `NET_AFTER_OTA_DEDUCTIONS`, or any other model as a safe default. Raise `MISSING_PAYMENT_RULE` and treat that reservation's Expected Settlement, commission, VAT, PB1, and Net Revenue as **incomplete, not final** — excluded from finalized report totals — until a rule is configured. This applies with the same force as rule 2: guessing a default here is inventing a business rule.

## Stack (as specified, don't deviate without discussion)

Next.js, TypeScript, Tailwind CSS, shadcn/ui, Supabase/PostgreSQL. AG Grid is approved specifically for the Monthly Performance matrix if evaluation confirms it's warranted — not for every table.
